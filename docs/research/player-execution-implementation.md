# 常驻玩家执行环境实施记录

## 行为与边界

本记录描述常驻执行阶段的 `paper@0.2.0` / v2 内部接口；后续方法调用 API 合并进同一未发布发行，当前接口见[API 实施记录](player-api-implementation.md)。该阶段每场每位玩家仍有独立 Node 子进程，使用原有同步 QuickJS-WASM；Runtime/Context、玩家模块和可信 SDK 在本场成功 tick 间复用。没有切换 V8、增加免费初始化预算或改变默认 CPU/堆/Memory 限额。

首次及环境重建后的 tick 计费玩家模块编译、顶层初始化、入口、SDK 调用、日志格式化及输出序列化；热 tick 只调用已经加载的入口。可信 Runtime、包装器、SDK 初始化和每 tick 输入注入不计入玩家 CPU，父进程墙钟看门狗继续生效。

全局变量、闭包、Map、TypedArray、SDK 状态和保留的观察引用都是受同一堆预算约束的易失缓存。每 tick 注入独立的观察和已提交 Memory，保留旧引用不会自动更新为新 tick 的数据。日志条数、字节预算、截断标记、CPU 起点和失败标记逐 tick 重置，Promise jobs 始终不执行。

任一玩家失败都会丢弃易失环境：包括异常、CPU/堆/栈超限、无效或超限 Memory、非法动作，以及父进程游戏解析器才发现的非法动作。当前 tick 使用默认动作，候选 Memory 丢弃；下一 tick 重新初始化模块与 SDK，仅恢复父进程持有的上次成功 Memory。正常的玩家错误只重建 VM，进程仍复用；墙钟超时、崩溃等沿用原有进程重建和代次机制。

可信包装器只初始化一次，并捕获 JSON.parse 等原始函数；后续输入不通过玩家可替换的全局 JSON/eval 路径。固定 console 入口的日志接收回调逐 tick 更新，避免日志归到前一 tick。临时 QuickJS 句柄逐 tick 释放，只有入口与可信闭包等必要句柄保留至 VM 结束。

保留的玩家堆可能挤占下一 tick 的输入分配；该情形归玩家 HEAP_LIMIT 并清空缓存，而首次干净环境中的可信初始化失败仍是系统失败。进程级内存隔离、单请求约束、IPC 长度/排队上限和迟到消息校验保持原有路径。

## 升级与旧发行

规则、观察和动作结构未改变，但模块及全局状态语义已不兼容，所以发布新游戏发行并递增 botProtocolVersion。服务端已有协议匹配检查会要求旧策略重新上传，排位保留；官方 bot 正常走相同沙箱。

v1 没有用户，不提供兼容。网页、根 CLI 和开发包仅注册当前 paper@0.2.0 / v2；旧观察解析、历史发行选择与 v1 回放注册均移除，发行或协议不匹配会拒绝。

没有迁移或改写用户数据库，也没有覆盖本地已有开发包、发布 npm 或推送代码。

## 性能测量

[基准脚本](player-execution-benchmark.mjs)和[常驻执行结果](player-execution-persistent.json)使用真实 Paper 观察与 SDK。升级前数据保留在[原始基线](player-execution-baseline.json)。以下为 Apple M4、Node.js 26.11.1 的开发机样本。

同一轮 300 对交替顺序的空策略调用：

| 沙箱内部调用 | 均值 | P50 | P95 |
| --- | ---: | ---: | ---: |
| 每次新建 Runtime | 989μs | 846μs | 1,630μs |
| 常驻 Runtime 热 tick | 215μs | 190μs | 393μs |

在这一配对微基准中，沙箱内部空策略调用墙钟减少约 78%，约为原来的 1/4.6。这包含 SDK、可信包装器、输入、玩家代码与序列化，不包含父进程、IPC、规则或回放，不能当作整局提升 4.6 倍。

新执行器的 3 场官方 bot 对战耗时为 3.80、3.64、2.86 秒，全部 600 tick、无执行错误且回放摘要匹配。终态摘要也与升级前官方 bot 样本一致。此次运行中纯引擎和空策略场景出现明显负载波动，例如空策略整局为 2.84–5.63 秒，不能据跨轮总耗时计算可靠的整局提升比例。宿主棋盘的重复校验和复制仍未优化，是后续完整比赛提速的主要方向。

常驻 VM 阶段没有实现 V8 对照、宿主 clone 优化、IPC 常量绑定或 Memory 序列化优化，也没有低配硬件实测。其后的宿主数据与序列化优化另见[后续实施与整局配对测量](player-data-optimization.md)，收益与本阶段分开评估。

### 后续整局配对补测

为得到可比较的整局提升比例，补做了同一轮 6 组配对、共 12 场正式采样，另有两个完整预热局不计入统计。固定双方官方 bot、seed 42–47、规则、SDK、WASM 和默认限额，旧/新执行器的先后顺序逐组交替，所有比赛串行运行、同场双方并行。

旧执行器来自调研基线提交 `af8bab107f3d58107541b3c713027d8ecb923d8d`，新执行器取当前工作区；两套沙箱源码以相同 TypeScript 配置转译到临时目录，使用共同的当前规则与引擎，均运行真实隔离子进程。源码摘要和环境记录在[配对原始数据](player-execution-paired.json)，[脚本](player-execution-paired-benchmark.mjs)可复现：

```sh
pnpm build:packages
node docs/research/player-execution-paired-benchmark.mjs --pairs 6 > /tmp/arena-paired.json
```

计时包含双方进程启动、600 tick 执行、规则结算、gzip 回放写入与 fsync、执行器关闭；回放读取/重演核验单独计时，不包含数据库排队、上传语法校验或浏览器渲染。

| 完整比赛 | 平均墙钟 | 中位数 |
| --- | ---: | ---: |
| 旧执行器，每 tick 新建环境 | 3.630s | 3.611s |
| 新执行器，常驻环境 | 2.862s | 2.846s |

按总耗时计算减少 **21.16%**，平均每场减少 **0.768s**，速度约 **1.27 倍**；各配对的耗时降低范围为 18.58%–22.91%。若把另行测量的回放读取与完整重演核验也计入，合计耗时降低约 **14.66%**。

12 场全部执行完整 600 tick、无执行错误；每一组旧/新执行器逐 tick 动作摘要和最终世界摘要均一致，回放也均重演通过。这一结果仅覆盖本机 M4 上的双方官方 bot 场景，不外推为所有玩家策略或低配机器的固定提升。

## 验证范围

自动测试覆盖模块/SDK 仅初始化一次、跨 tick 缓存、独立观察与 Memory、日志预算重置、跨 tick 内建函数污染、各类失败后的缓存清除、父进程动作拒绝、堆跨 tick 累积、缓存导致输入分配失败、进程死亡后的 Memory 恢复、批量比赛隔离，以及网页/CLI 的不匹配发行拒绝。

`pnpm check` 已通过：378 项测试通过、35 项按环境条件跳过，保留 3 条既有 web 副作用导入 lint 警告。已执行新版 sandbox benchmark 和上述完整比赛基准。`pnpm test:artifacts`（包含全量 `pnpm build`）也已通过：6 个打包包、12 个公开 exports、仓库外 NodeNext 类型、真实子进程常驻/失败恢复、600 tick 比赛、发行校验、编译后 API，以及 1 个独立 ZIP 开发包的下载/安装/对战/调试与回放流程。Linux cgroup 与真实 PostgreSQL 集成检查依赖相应环境，本机未配置时按测试条件跳过。
