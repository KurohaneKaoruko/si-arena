# 执行架构配对基准（2026-10-22）

完整比赛与批量运行均达到本次验收目标：两款游戏的官方对战单场中位耗时下降超过 25%，8 场批量耗时下降超过 40%。逐场比较的规范动作、终局结果和最终世界哈希一致，所有回放独立重演通过，没有玩家执行错误。

[原始测量 JSON](runner-architecture-benchmark.json) 保留每个配对样本、源码摘要、准备/启动/执行/压缩收尾/回放验证耗时、玩家 CPU、runner CPU 与峰值 RSS，以及独立资源探针。执行脚本为 [benchmark-runner.mjs](../../scripts/benchmark-runner.mjs)。

## 条件与方法

- 主机：Apple M4，10 个可用逻辑 CPU，macOS arm64；Node v26.11.1，isolated-vm 7.0.1，pnpm 12.14.0。
- 基线提交：`4b85c66a15c3d8ce158dafa044ba5399dcb8a76e`。修改前保存干净版本的生产包图及固定依赖，基线不链接重构后的 workspace 包；原始记录包含各基线包的 SHA-256。
- 两边使用同一份玩家源码、种子、参赛人数与每玩家 CPU/堆/Memory/墙钟预算。圈地 2 人，大逃杀 5 人；圈地保持完整 500 tick，大逃杀按相同规则终局。新发行分别为 paper@0.3.0、royale@0.2.0，玩家协议仍为 2、1。
- 每种模式与场景先排除一次预热；官方 bot 取 6 对相邻种子，其他场景各 2 对，交替执行前后版本，再取各自中位数。小样本场景用于覆盖负载，不能据此解释细微差异。
- 比较完整执行 API：包括进程启动、所有 tick、gzip 写入与背压、fsync、目标路径创建和进程退出；源码准备和完整回放验证单独计时。批量计时结束后再统一验证回放，验证不进入批量耗时。
- 日志开启场景在原入口外包一层，每 16 tick 打印一条相同日志；两边同样捕获、同样预算。计算循环每 tick 进行 25,000 次 Math.sqrt 并写入 Memory；大 Memory 场景保留 60KiB 字符串并逐 tick 更新计数。
- Royale 的可信 SDK 新增对数组方法的预先捕获，避免玩家篡改原型干扰下一 tick 工厂；SDK 接口相同，源码文本有这一差别。未通过缩短比赛、提高玩家预算或关闭某一侧日志取得提升。
- 无数据库、排队和浏览器渲染；计时期间不并行运行本次构建或测试。Linux 调度与文件系统的实际收益需要在部署环境复测。

## 阶段与资源

下表为官方 bot、关闭日志，单位 ms。准备只有一次同条件源码校验，其他阶段取 6 次中位数。压缩随 tick 流式进行，收尾列仅测量 finish 的尾缓冲、gzip 完成和同步落盘；此前的压缩成本包含在比赛区间。

| 游戏 | 版本 | 准备 | 启动 | 比赛区间 | gzip 收尾与 fsync | 回放验证 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| paper | 重构前 | 37.5 | 34.9 | 383.2 | 9.5 | 140.8 |
| paper | 重构后 | 40.2 | 33.7 | 221.4 | 10.9 | 81.3 |
| royale | 重构前 | 39.5 | 47.4 | 1891.7 | 11.5 | 845.3 |
| royale | 重构后 | 43.1 | 36.4 | 842.3 | 11.1 | 368.2 |

这些阶段不是可相加的互斥分解：基线比赛区间包含逐玩家进程启动，新版比赛区间位于已就绪 runner 内；新版首次 isolate/SDK/玩家模块初始化仍计入比赛区间。启动列在基线记录最慢玩家进程就绪，在新版记录 runner 就绪与源码绑定。总耗时才是严格对照口径，原始记录另外保存新版候选发布耗时。

资源探针另起独立测量进程执行一次相同种子的完整比赛，不干扰上述配对计时。CPU 为驱动进程及其等待回收的全部后代累计用量，含驱动启动与模块加载，不含回放验证；它不是玩家 CPU 预算。每个 tick 的玩家 CPU 仍来自各 isolate 的 cpuTime。

| 游戏 | 版本 | 总 CPU ms | 进程树采样峰值 MiB | 最大单进程内核峰值 MiB |
| --- | --- | ---: | ---: | ---: |
| paper | 重构前 | 802.3 | 289.9 | 110.2 |
| paper | 重构后 | 527.5 | 233.3 | 161.9 |
| royale | 重构前 | 4807.6 | 752.5 | 156.8 |
| royale | 重构后 | 2299.4 | 319.6 | 247.7 |

RSS 采样覆盖驱动与所有后代，每轮间隔 20ms 加一次 ps 查询耗时，因此不是精确的瞬时峰值或 cgroup 硬限验证；最后一列是最大单进程高水位。新版把多位玩家合并到一个进程，单进程峰值增加、整个进程树的占用降低。所有 16 个场景的探针数据均在原始 JSON 中，新版还直接报告比赛进程的内核峰值 RSS 和累计 CPU。

## 复现

从仓库根执行，保持相同 Node/pnpm 与资源条件，基线目录应使用其自身锁文件和构建产物：

```sh
git worktree add --detach ../si-arena-baseline 4b85c66a15c3d8ce158dafa044ba5399dcb8a76e
pnpm --dir ../si-arena-baseline install --frozen-lockfile
pnpm --dir ../si-arena-baseline build:packages
pnpm bench:runner --baseline ../si-arena-baseline --pairs 6 --all --resources --out ./runner-benchmark.json
```

`--resources` 需要 Python 3 与 POSIX ps；省略它仍可运行配对耗时、阶段与逐 isolate CPU 测量。`--game paper` 可筛选游戏。路径由调用方指定，不依赖本机临时目录；原始 JSON 的 baseline 路径只是本次冻结包图的位置。

## 验证范围

`pnpm check` 通过：55 个测试文件通过，471 项测试通过，45 项因环境条件跳过。`pnpm test:artifacts` 内的完整 `pnpm build` 通过；仓库外真实 Node 和严格 NodeNext 验证 8 个公开包、18 个 exports，并完成两款游戏独立 ZIP 开发包的冻结安装、官方对战、批量运行、日志、删除 bot 后重演和本地查看器验证。

已在 macOS arm64 验证普通异常、CPU/墙钟、堆超限、恶意原型、微任务、非法动作、Memory 原子回滚与下一 tick 恢复；同场其他 isolate 正常完成，比赛进程退出不发布候选，其他比赛继续。批量种子顺序、独立失败、取消清理、跨场状态隔离和有界 IPC 有自动化覆盖；源码包含大量控制字符或需要拆帧时仍可正确校验和绑定。

真实 Linux cgroup/OOM 测试需要独立 Linux 委派目录；PostgreSQL 结算、租约与容量领取测试需要 ARENA_TEST_DATABASE_URL。本机未配置这两个环境，相关测试跳过，不能把本次 macOS 结果视为 Linux 内存硬限或数据库结算集成验证。stackBytes 沿用现有保留字段及 V8 栈溢出处理，没有新增精确栈字节控制。
