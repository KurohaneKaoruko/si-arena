# 玩家代码沙箱

执行器采用 isolated-vm 提供的 V8 isolate 与独立执行子进程。线上与本地共享这套实现，限额以 [资源限额](resource-limits.md) 为准。

## 选型与边界

isolated-vm 在 Node 进程内创建独立的 V8 isolate：独立堆、独立上下文、没有 Node 全局，宿主只通过显式复制的原始值和受控引用与之交互，并提供堆上限、墙钟中断与 isolate 线程 CPU 计时。[官方项目](https://github.com/laverdet/isolated-vm)。玩家代码得到 V8 的完整 JIT，计算密集策略比解释执行快一个数量级以上；每 tick 成本以实测为准，见[沙箱包说明](../../packages/sandbox/README.md)。

isolated-vm 的堆上限在 V8 GC 时生效，是近似上限而不是逐字节硬限；灾难性错误（V8 无法继续）要求终止宿主进程。本平台每位玩家独占一个执行子进程，线上再套 cgroup `memory.max`：isolate 被销毁或进程退出都只影响该玩家，父进程重建。隔离边界由 isolate、独立子进程与操作系统限制共同构成，不把任何一个库直接等同于完整安全运行环境。

不使用 Node.js `vm` 作为不可信代码的安全边界。[Node.js 文档](https://nodejs.org/api/vm.html)明确说明它不是安全机制。曾采用的 QuickJS-WASM 方案（2026-10 前）已移除：其解释执行使玩家计费 CPU 高 13–18 倍，且不再有它独有的安全属性。

## 进程与生命周期

主比赛运行器持有世界、代码的临时副本以及已提交 Memory。每场每位正在行动的玩家使用独立的执行子进程，避免一个执行器崩溃清掉其他玩家上下文。进程可在本场复用，不在每 tick 启动 Node.js。

每场每位玩家建立独立的常驻 V8 Isolate 与 Context。可信封装、SDK 和玩家模块只在环境创建时加载；成功 tick 间保留全局变量、闭包和 SDK 状态作为易失缓存。每 tick 用预先捕获的 JSON.parse 注入全新的观察与已提交 Memory，重置日志预算与 CPU 计量，不通过已被玩家修改的全局函数处理输入。框架句柄仅保留必要的入口和可信闭包，每 tick 的临时句柄及时释放。

任一执行失败后丢弃环境，包含父进程才判定的非法游戏动作。下一 tick 重建模块和 SDK，仅恢复上次成功的 Memory，不恢复整个 JS 堆或旧调用栈。全局缓存占用同一个 isolate 堆预算，缓存挤占下一 tick 输入分配时归玩家 HEAP_LIMIT；首次可信初始化无法完成仍属系统失败。isolate 因堆上限被销毁时丢弃对应环境；V8 报告灾难性错误时执行进程直接退出，子进程失去响应或退出时由父进程重建。

首版不支持从主 worker 崩溃中恢复整场比赛。玩家子进程重启则可以继续，因为权威世界与已提交 Memory 在主运行器中。

## 输入输出

输入仅包括自包含源码、玩家 ID、当 tick 观察、该玩家已提交 Memory、可信游戏 API 工厂和限额配置。玩家入口接收 `{ game, Memory }`；game 的形状和动作方法完全由游戏定义。可信工厂在沙箱内接收冻结观察和私有 submit/reject 闭包，构建每 tick 独立的视图并初始化默认意图；不向玩家直接暴露提交通道。工厂异常属于系统错误。动作方法只更新本 tick 候选命令，全部执行正常且输出验证通过后一次提交。非 undefined 入口返回值为 ENTRYPOINT_ERROR；reject 与旧 tick 的提交调用锁定 INVALID_ACTION，玩家 catch 也不能恢复本 tick 提交。

输出为有效 JSON 动作、候选新 Memory、诊断与本地有界日志。宿主不能直接遍历玩家对象、调用玩家 getter 或接收可调用引用。动作与 Memory 在受限环境中完成受控序列化，再在宿主按协议验证。

每个比赛 tick 请求和其全部结果、日志都携带 `(matchId, playerId, tick, executionId)`，executionId 标识当前子进程代次。每个进程同时至多处理一个 tick。父进程只接受当前待处理请求的消息；超时、结束或进程被替换后将请求封闭，丢弃迟到动作和日志，不能将上一 tick 结果当成下一 tick 提交。结果和日志使用同一有序 IPC 通道。帧长度在解析 payload 前检查，日志排队缓冲也必须有界。语法校验请求使用独立 validationId 和对应通道，不创建比赛 ID。源码、可信 SDK、限额和日志开关在进程就绪后一次绑定，进程重建后重新绑定；每 tick 请求只携带身份、观察、已提交 Memory 与日志余额。

包装器在加载玩家代码前捕获可信内建函数和协议校验器，以闭包保存；玩家修改全局 JSON、Object 原型或 console 不得替换宿主提交路径。Memory 使用严格 JSON 数据规则，不通过宿主对象合并传播原型属性。错误提取和日志格式化在受限环境内完成；预算已耗尽时使用宿主生成的固定错误类型，不为读取异常消息再次无限执行玩家 getter。

宿主侧复用 protocol 的严格 JSON 编码与复制，不另行维护校验规则；对象中的隐藏属性、访问器和符号键均被拒绝，不静默丢弃。复制在一次遍历中完成严格校验、等价 JSON UTF-8 字节计数与独立对象构造，避免先编码全文再解析的中间字符串；共享引用展开，循环引用拒绝，原型键按普通数据保留，数字 -0 归一化为 0。`snapshotJson` 用同一遍历生成深冻结快照并登记其字节数；快照跨边界传递时按引用复用、不再遍历，`cloneJson` 复制快照时也不重复校验。isolate 内部的序列化器在隔离环境中独立运行，字符访问函数在玩家加载前绑定，逐字符计数不临时分配调用参数数组。

首次及重建后的玩家模块编译/初始化、顶层代码，以及每 tick 的入口调用、动作方法、日志格式化和输出序列化都计入所在 tick 执行预算；热 tick 不再次加载玩家模块。框架启动、可信引导、SDK 初始化与每 tick 视图构建属于平台固定开销，不计入玩家预算、不被 CPU 中断，由墙钟兜底；不能把玩家顶层计算排除在预算外。执行进程在绑定源码时完成静态检查，计入启动预算而不是第 0 tick。V8 的分层编译在玩家自己的 isolate 内随 tick 推进，无需预热；第 0 tick 含模块求值，通常仍只有后续 tick 的数倍。

## 资源策略

| 资源 | 限制位置 | 超限行为 |
| --- | --- | --- |
| 源码字节数 | 上传 API 与本地加载入口 | 上传/加载拒绝，不替换现有代码 |
| isolate 堆（含 ArrayBuffer） | isolated-vm `memoryLimit`；被拒绝的单次分配为 RangeError | 未捕获时当 tick 失败；堆整体超限时 isolate 被销毁并重建环境 |
| 调用栈 | isolate 执行线程的栈（isolated-vm 固定，约 5000 层递归；`stackBytes` 不改变它） | 未捕获溢出时当 tick 失败，记录诊断 |
| CPU 时间 | 玩家求值阶段 isolate 线程的 CPU 用量 + 每 1ms 轮询 | 销毁 isolate，禁止提交当 tick 输出 |
| 墙钟等待时间 | 父进程看门狗 | 终止执行子进程，记录超时或执行器错误 |
| Memory | 序列化后 UTF-8 字节数与 JSON 协议 | 当 tick 失败，保留旧 Memory |
| 玩家动作及执行结果 | 沙箱包装器与父进程 | 拒绝，使用默认动作 |
| 平台输入及控制消息 | 父进程与发布配置校验 | 超限为系统错误，不算玩家失败 |
| 本地日志 | 单条、每 tick、整场有界缓冲 | 截断并提示，不改变游戏行为 |
| 进程总内存 | 线上独立 OS 限制 | 隔离失败进程，父进程决定诊断与重建 |

isolate 堆限制不等于整个 Node 进程的 RSS 限制，也不包含所有宿主缓冲区。V8 后台线程、Node 开销、IPC 缓冲仍需单独预算。玩家上下文只有纯 ECMAScript：没有 Node 全局，引导时删除 `WebAssembly`（后台线程编译不计费）、`SharedArrayBuffer` 与 `Atomics`（没有线程能唤醒阻塞的 `Atomics.wait`）。

CPU 使用 isolate 自身线程的计时（isolated-vm `cpuTime`）而非 `Date.now()` 差值；进入玩家阶段时记录起点，计费为差值。执行环境为 Node.js 26。执行器读取该游戏发行的完整资源配置，默认每 tick 20ms CPU、500ms 墙钟，不能在代码中写死为所有游戏的固定值。

isolated-vm 只提供墙钟中断，CPU 预算由执行进程每 1ms 轮询 `cpuTime` 并在超限时销毁 isolate 实现；轮询有粒度，不能承诺每条 JS 指令后检查。isolate 调用本身带该游戏 `wallMs` 的墙钟超时，父进程墙钟再兜底。正常输出前再次检查预算；框架已确认的资源失败必须锁定为失败，不能靠玩家 catch 异常后返回动作绕过。

V8 把被拒绝的单次分配（ArrayBuffer、超长数组或字符串）和栈溢出作为可捕获的 `RangeError` 抛出：玩家捕获后属于普通 JS，因为上限已经生效、没有任何越界分配发生；未捕获时包装层按 `HEAP_LIMIT` / `STACK_LIMIT` 记账。堆整体超过 isolate 上限时 isolated-vm 直接销毁 isolate，玩家无法捕获，当 tick 记 `HEAP_LIMIT` 并重建环境。CPU 超限与墙钟超时同样终止执行，`catch` 无法恢复。入口返回后 V8 排空微任务队列：此时动作与 Memory 已序列化，任务改不了提交内容，但其 CPU 计入同一 tick，失控任务使该 tick 失败。错误结果使用捕获的原始函数和手工 JSON 封装，不能被玩家安装的 `Object.prototype.toJSON` 改写。分配失败、极大字符串或正则、深递归、微任务均纳入验收。

isolated-vm 7 随 npm 分发预编译二进制（macOS arm64、Linux x64/arm64 的 glibc 与 musl、Windows x64），`node-gyp-build` 在加载时按平台与 Node ABI 选取；pnpm 不运行它的安装脚本（`allowBuilds` 中显式为 false），线上镜像与开发包的 `--ignore-scripts` 安装都不需要编译器。其他平台需要 C++ 工具链并放行构建。使用和性能记录见 [沙箱包说明](../../packages/sandbox/README.md)。

平台默认源码为 256KiB、isolate 堆为 32MiB（isolated-vm 下限 8MiB，更小的配置按 8MiB 建立）、调用栈 `stackBytes` 保留为 256KiB 仅供协议兼容：isolated-vm 在自己的线程上执行玩家调用，V8 `--stack-size` 不作用于这些线程，实际深度由其线程栈固定（约 5000 层递归）、Memory 为 64KiB，游戏可按字段覆盖。每个 worker 并发 2 场圈地比赛，每玩家使用独立执行进程；线上和本地读取同一游戏发行的完整预算。其他数据与日志限额见 [资源限额](resource-limits.md)。

## 提交与失败

每 tick 的动作和新 Memory 作为一个提交单元。必须同时满足正常完成、入口返回合法、动作合法、Memory 可序列化且大小合规、无已确认超限，才提交二者。

失败时丢弃候选输出，使用游戏默认动作，旧 Memory 不变；已捕获日志和错误可以保留。失败后的下一 tick 在全新 Isolate 中重新调用，不恢复旧调用栈或全局缓存；成功 tick 保留易失环境。反复失败的代码可每 tick 再失败，不能无限重试同一 tick。

错误类型至少包括 `RUNTIME_ERROR`、`CPU_LIMIT`、`HEAP_LIMIT`、`STACK_LIMIT`、`MEMORY_LIMIT`、`MEMORY_INVALID`、`INVALID_ACTION`、`ENTRYPOINT_ERROR`、`EXECUTION_TIMEOUT`、`EXECUTOR_ERROR`。无法识别的进程退出归为 `EXECUTOR_ERROR`，不能把所有崩溃都报告为 OOM。

源码语法校验也在独立执行进程中进行，仅运行受限 AST 检查与同版 V8 模块编译（不实例化、不求值），不调用入口、不产生比赛。使用目标游戏的代码、内存、栈、CPU 和墙钟限制。校验进程不复用玩家比赛的进程配额，服务端单独限制同时校验数为 2，超出返回 429。

比赛 tick 路径中的同一受限 AST 检查属于平台策略而非玩家执行：每个执行子进程对每份源码只运行一次，且不计入该 tick 的 CPU 预算，进程重建后重新校验一次。只有校验通过的源码进入缓存；校验失败的源码不缓存，该子进程的每个 tick 都重新校验并返回 `ENTRYPOINT_ERROR`。

## 日志与错误捕获

本地 console 包装器按打印顺序输出有界文本快照，父进程保存已经收到的记录。最后一条日志尚未通过 IPC 发出时进程被终止，可能丢失；界面不承诺保留未捕获内容。已收到的日志即使当前 tick 失败仍保留。

服务端 console 使用空实现，不序列化或转发参数；调用本身仍属于玩家代码执行。错误记录由执行器生成受限结构，消息、堆栈和总字节数有上限，不能直接把任意 throw 对象作为宿主异常处理。

## 线上权限

- 无网络访问，无数据库或存储凭证，不继承业务进程的完整环境变量。
- 仅允许加载可信执行器和 isolated-vm 二进制，不暴露文件 API 给玩家。
- 独立进程资源限制、低权限用户、受限文件系统与系统调用。
- IPC 仅接受固定协议与有界数据，主 worker 不执行来自玩家的宿主 JS。
- 受控并发，避免进程数量或已缓存代码耗尽整机资源。

执行器创建时显式选择 `local` 或 `cgroup-v2`。前者用于本地调试，不承诺整个进程的 RSS 硬上限；后者要求 Linux 委派目录，创建 isolate 前将该玩家进程加入独立子组，设置 memory.max、禁止 swap 并限制 pids，配置失败即拒绝运行。业务调用方负责低权限身份、容器网络/文件系统/系统调用策略和容量调度。cgroup OOM 事件是进程因内存被终止的证据；没有该证据的退出按执行器错误处理。

子进程自身的 Node API 不应因任意宿主回调或对象引用泄漏而交给玩家。只注入必要的纯数据和沙箱内部函数。

## 执行器验收

在正式接入排位前，至少验证：死循环可结束；超大分配不拖垮其他玩家；深递归可诊断；输出与 Memory 序列化受限；错误后下一 tick 可运行；超限前已捕获日志可读；进程被终止后父运行器继续；本地和线上使用同一执行协议。

分别测量首次及重建后的 Isolate 创建/源码加载/SDK 初始化、热 tick 的输入/序列化/IPC，以及跨 tick 堆增长的成本，并记录软件版本与硬件。此项是必要的沙箱验证，不是平台面向玩家提供的试跑模式。
