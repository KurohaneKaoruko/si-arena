# 排位与匹配

## 触发条件

比赛必须由某个用户主动发起。用户上传代码、登录、下线或后台时钟变化均不创建比赛。上传后显示“匹配”入口，由用户另行操作。

发起者必须在该游戏提交与当前代码协议兼容且体积合规的代码。其他合格用户即为可选对手，无需在线、进入等待队列或确认邀请。官方 bot 也在选手池中。不兼容升级后旧代码暂停参赛并提示重新上传；兼容升级继续使用，排位分均保留。

后台只处理用户已经创建的匹配请求，不自行产生新的竞技请求。

## 首版匹配流程

首个游戏采用两人局：

1. 验证身份、代码是否存在以及请求是否重复。
2. 在相同游戏的非本人选手中，优先寻找排位分接近的普通用户。
3. 如果没有处于合适分差范围的普通用户，立即使用官方 bot，不等待真人上线。
4. 写入比赛任务，返回比赛 ID。
5. worker 开局时读取双方最新代码，开始执行。
6. 完成后同时更新双方排名所依据的排位分。

“立即匹配”意味着立即确定可用对手并创建任务；服务器资源繁忙时仍可能短暂等待 worker，不承诺零排队延迟。

匹配分差上限为 250 分。先取范围内所有合格普通选手；当存在其他候选时排除最近一场已完成比赛的对手，再从剩余选手中选择绝对分差最小者，最小分差并列时随机。范围内只有一个候选时允许重复。没有普通候选时直接选择官方 bot，不对官方回退应用分差限制，也不等待真人上线。任何路径都排除本人。

## 官方 bot

- 官方账号在每个游戏有一份独立代码和独立排位分。
- 源码与本地开发包一同公开，运行环境与普通选手相同，不读取隐藏状态。
- 参与正常计分，不固定排位、不额外赠送积分、不设独立排行榜。
- 可以同时作为多场独立比赛的对手，每场使用独立的沙箱和 Memory。
- 官方身份由系统字段标记，特殊用户名只负责展示。

至少一个官方 bot 必须随游戏发布成功安装，才能保证首个真实用户有对手。

## 得分与排名

| 概念 | 定义 |
| --- | --- |
| 局内得分 | 由游戏规则计算，例如领地面积 |
| 比赛名次 | 由游戏根据淘汰、得分、平局等规则生成 |
| 排位分 | 平台根据名次与对手排位计算，按游戏独立 |
| 排行榜 | 按该游戏排位分排序，并显示比赛数 |

排位使用 Elo。两人局中，A 的预期得分为 `EA = 1 / (1 + 10 ** ((RB - RA) / 400))`；实际得分 `SA` 在胜、平、负时分别为 `1`、`0.5`、`0`。更新 `RA' = RA + K * (SA - EA)`，B 对称计算。

初始排位分为 1000，K 为 32。内部使用 `numeric(12,6)`，每对选手先把 A 的变化四舍五入到 6 位小数，再以相反数更新 B，确保单次变化之和为 0。界面显示 2 位小数，名次按内部精确分数计算；精确分数相同显示并列，展示顺序按稳定用户 ID 排序。

多人游戏将名次转换为每对选手的胜、平、负，使用 `K / (人数 - 1)` 计算每个无序选手对的变化，保留 6 位小数后对双方分别加减，再累加所有对手的变化。相同名次按平局计算。圈地固定两人，使用上述两人公式。

## 并发与重复请求

- 主动发起使用幂等请求标识，网络重试返回同一比赛。
- 限制同一用户在同一游戏只有一个未完成的主动请求，避免连续点击重复创建任务。
- 数据库对未完成主动请求建立部分唯一索引，不能仅用“先查询再插入”处理并发；不同请求同时到达时也只能创建一场。
- 被动成为对手不依赖在线状态，可参与多场独立比赛；总执行量由 worker 并发限制控制。
- 结算按稳定顺序锁定双方排位行，以结算时的排位计算变化，避免并发覆盖。
- 每场比赛最多结算一次；任务重投递不能重复加减分。
- 官方 bot 不受“同一时间只能被一个人挑战”的限制。

匹配记录当时分差，但不承诺长时间排队后的分差仍相同。完成前用户更新代码不重置排位，也不改变本场固定代码。

## 失败分类

玩家 JS 异常、超时或超限属于比赛内事件：转换为当 tick 默认动作，正常比赛和计分，不能因主动抛异常逃避败局。

规则引擎崩溃、主 worker 丢失或回放无法可靠保存属于系统失败：本场不更新排位，不伪造胜负。只重试持久化和结算等幂等操作，不使用已经被替换的代码重新跑一场并冒充原比赛。

比赛排队期间若用户的新代码不再兼容本场已冻结的发行或超过其源码上限，开局检查使任务失败、不计分，并提示重新主动匹配，不恢复旧代码。
